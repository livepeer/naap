Dual-Key Side-by-Side: Daydream + pymthouse (NaaP)

Can the Daydream key path (signer.daydream.live, type:lv2v) and the pymthouse / NaaP key path (per-key DMZ signer, type:byoc) run side by side against one SDK-service instance — selected by SDK-service config, by an agent/MCP per-request config, or by the key format itself? Feasibility, desirability, and the how-to.

Read-only analysis. Grounded in STORYBOARD-SIGNER-ROUTING.md, pymthouse-e2e.md, BPP-VALIDATE-V2-NAAP-DISCOVERY.md, and apps/web-next/src/app/api/v1/keys/validate/route.ts. The signer-routing code (simple-infra/sdk-service-build/app.py, Storyboard lib/sdk/*) lives in sibling repos; citations use the line numbers recorded in the investigation doc.

TL;DR — Yes, side-by-side is possible, and it is mostly already built. The decision node (_effective_signer in the SDK service) already inspects the bearer per-request: a naap_ key that resolves a signerSession goes pymthouse; anything else (a Daydream sk_ key) falls back to the static signer.daydream.live. Today it is "either/or" only because the enabling flags are process-wide env gates that are unset in production. Flip SIGNER_FROM_VALIDATE=1 + set AUTH_VALIDATE_URL on a single instance and both keys route correctly on the same box.

Recommendation: route by key format automatically (Option A, already latent) — the simplest robust path — and harden one gap: fail-closed for a naap_ key that can't resolve a session (don't silently bill Daydream's shared wallet). Add an optional explicit override (Option B) later only if a caller needs to force a path. An agent/MCP config is not required for MVP because the key format is already an unambiguous discriminator.

2. Option A — SDK-service per-request routing (by key format)

The service inspects the incoming bearer and picks the signer per-request. This is what the code already does; the work is to make it safe to run permanently with the gates ON, and to remove the process-wide "flip" semantics from the mental model.

Decision logic (target)

def _effective_signer(bearer):
    # A) Daydream key → static signer, lv2v (today's default; unchanged)
    if not bearer.startswith("naap_"):
        return (SIGNER_URL, caller_headers)         # signer.daydream.live → lv2v

    # B) naap_ key → resolve per-key pymthouse session
    session = _resolve_validate_session(bearer)     # POST AUTH_VALIDATE_URL
    if session and session.url:
        return (session.url, session.headers)       # DMZ signer → byoc

    # C) naap_ key but NO session  → HARDEN: fail-closed, do NOT fall to Daydream
    raise Reject(402, "naap_ key could not resolve a signer session")

Default = today's behavior: with gates OFF, every request is Daydream/lv2v — zero regression. With gates ON, a Daydream sk_ key is byte-for-byte the same path (it never matches naap_).

3. Option B — Agent/MCP passes an explicit config per request

Storyboard/MCP includes an explicit provider selector that flows to the SDK service, which honors it over (or alongside) key-format inference.

Storyboard / MCP side

  • provider-core.ts: extend the per-call input with signerProvider?: "daydream" | "pymthouse" (distinct from the existing base-URL NAAP_PROVIDER, which only picks the service URL).
  • sdk-call.ts: forward it as a header, e.g. X-Naap-Signer-Provider: pymthouse, next to the unchanged Authorization.
  • Both key types must target the same SDK-service instance — i.e. do not use STORYBOARD_PROVIDER_SWITCH to split base URLs, or the per-request selector never reaches one box.

SDK-service side

  • _effective_signer reads X-Naap-Signer-Provider first.
  • Precedence: explicit header → key-format inference → static default.
  • Guard rails: pymthouse requested with a non-naap_ bearer ⇒ reject (can't mint a session); daydream requested with a naap_ key ⇒ allowed but bills the shared wallet — log loudly / gate behind an allow-list.

Option B is strictly additive on top of Option A. It buys override power (force a path regardless of key), at the cost of a new contract field on three surfaces and new mismatch cases to validate. It is not needed to make the two keys coexist.

4. Feasibility & desirability

QuestionVerdictWhy
Possible without breaking the Daydream path? YES Non-naap_ keys never enter the pymthouse branch — they hit the unchanged static SIGNER_URL → lv2v. Daydream expects lv2v; pymthouse expects composite/byoc; each key type deterministically lands on its own signer + payment type.
Achievable per-request on one instance? YES The per-request key check already exists in _effective_signer. Only the two env gates are process-wide, and they're gate-conditions, not the router itself.
Key-format auto-routing cleaner than explicit config? YES The key is the intent: a naap_ key means "bill my NaaP account"; a Daydream key means "use the shared Daydream wallet." An extra provider field is redundant with the key and adds a mismatch surface (provider says X, key implies Y).
Is an agent/MCP config needed? NO (for MVP) Add it later only as an override. Default routing needs nothing beyond the key.

Recommended approach: Option A — route by key format, gates ON, fail-closed with Option B as an optional later override. Simplest robust path; avoids over-engineering; no new request contract required to ship.

5. Risks

R1 · Silent mis-attribution on session failure (HIGH). Today a naap_ key whose validate returns no session falls back to the Daydream signer → billed to the shared Daydream wallet, not the caller. Fix: fail-closed (402/401) for naap_ keys with no resolvable session. This is the single most important hardening for side-by-side.
R2 · Payment-type mismatch. Payment type is derived purely from the signer hostname (signer.daydream.live → lv2v, else byoc). As long as the signer URL is correct, the type follows automatically — no extra code. Risk only if a wrong URL is ever handed through.
R3 · Base-URL split defeats side-by-side. If Storyboard uses STORYBOARD_PROVIDER_SWITCH to send naap_ traffic to a different SDK service than Daydream traffic, the two keys never share an instance. For true side-by-side, point both at one instance that has the gates ON.
R4 · Latency + validate dependency. Every naap_ request adds a /keys/validate round-trip and hard-depends on that endpoint. Daydream keys skip it entirely. Consider a short-TTL session cache; ensure validate availability SLO covers the pymthouse path.
R5 · Env guard rail. simple-infra/scripts/validate-envs.sh:141-155 rejects SIGNER_FROM_VALIDATE=1 unless AUTH_VALIDATE_URL is set. Honor it — set both together in the overlay.
R6 · Metering attribution correctness. Daydream → shared wallet → api.daydream.live/webhooks/remote-signer; pymthouse → caller's funded wallet → OpenMeter. Verify each key type lands in the correct meter after enabling side-by-side.

6. How-to — phased, flag-gated

Phase 0 — Verify latent behavior (no code)

  • Confirm in app.py that _effective_signer returns the static SIGNER_URL for a non-naap_ bearer even when the gates are ON (read _resolve_validate_session + the branch, app.py:1001-1091).
  • Confirm NaaP validate accepts naap_ only (already true — keys/validate/route.ts:5).

Phase 1 — Harden fail-closed (small code change)

  • In _effective_signer: when bearer is naap_ and no session resolves, return a reject (HTTP 402/401) instead of falling through to SIGNER_URL. Guard behind a flag, e.g. NAAP_FAIL_CLOSED=1, defaulting OFF so nothing changes until opted in.
  • Unit-test both: naap_+session ⇒ DMZ signer; naap_+no session ⇒ 402; sk_ ⇒ static signer.

Phase 2 — Enable side-by-side on ONE instance (config only)

# simple-infra overlay for the shared instance
AUTH_VALIDATE_URL:    https://operator.livepeer.org/api/v1/keys/validate
SIGNER_FROM_VALIDATE: "1"
SIGNER_URL:           https://signer.daydream.live   # still the daydream fallback
NAAP_FAIL_CLOSED:     "1"                             # from Phase 1
  • Storyboard: point both key types at this one instance (do not split base URLs by provider).
  • Run validate-envs.sh — the SIGNER_FROM_VALIDATE+AUTH_VALIDATE_URL pairing must pass.

Phase 3 (optional) — Explicit override (Option B)

  • Add signerProvider to provider-core.ts; forward X-Naap-Signer-Provider in sdk-call.ts.
  • Honor it in _effective_signer with precedence override → key format → default, and reject impossible combos (pymthouse + non-naap_).

Bottom line. Side-by-side is feasible and desirable, and the router already exists — it just needs its process-wide env gates turned on for one instance plus a fail-closed guard so a naap_ key never silently bills Daydream. Key-format auto-routing (Option A) is the recommended default; an agent/MCP override (Option B) is a clean, optional add-on, not a prerequisite.
