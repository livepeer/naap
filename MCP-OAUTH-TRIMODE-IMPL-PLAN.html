1. Executive summary & scope boundary

Thesis: tri-mode auth is a head change, not a tail change. Introduce one thin module — the Auth Resolution Layer (resolveAuth(headers) → ResolvedCredential) — in Storyboard, and make P0/P1/P2 three credential providers feeding it. Nothing below that boundary (MCP tool handlers, sdkCall, the SDK service, the gateway, the signer, the orchestrator) learns that OAuth exists. That single constraint is what keeps this from becoming a regression engine.

1.1 What ships, in three sentences

  1. Foundation (PR-01…PR-03, Storyboard, no flags): lock today's behavior with golden tests, then extract resolveAuth() as a behavior-preserving refactor of extractAuthOrDemo, and add a log-only plane/scheme classification so we can observe traffic mix before changing anything.
  2. OAuth head (PR-04…PR-08, Storyboard, MCP_OAUTH_ENABLED default OFF): real RFC 9728 Protected Resource Metadata + Authorization Server metadata, an RFC 9728-compliant WWW-Authenticate challenge, a restart-safe mcp_at_* session store, the authorize/callback/token broker, and exactly one new branch in resolveAuth that turns mcp_at_* into a bound forwardBearer.
  3. Mint providers + billed tail (PR-09…PR-16): Scenario A mints via a new NaaP internal route wrapping the existing createPymthouseApiKey; Scenario B mints via a Storyboard-held M2M call to the same Builder endpoint; simple-infra gets a build-time guard for the LR gateway import plus canary-only key-routing config. Both scenarios emit the same composite shape, so there is one billed tail to test.

3.2 The ResolvedCredential contract

// lib/mcp-server/auth/resolve.ts — the ONLY new abstraction this plan adds.

/** Billing-plane hint for logs and metrics ONLY. The SDK re-classifies
 *  independently via classify_key(); this field must never drive routing. */
export type BillingPlane = "daydream" | "pymthouse" | "unknown";

export interface ResolvedCredential {
  /** Verbatim bearer forwarded to the SDK. Always a shape the signer
   *  accepts: sk_* or app_*_pmth_*. Never mcp_at_*. */
  forwardBearer: string;

  plane: BillingPlane;

  metadata?: {
    source: "api_key" | "oauth_session" | "demo";
    /** Audit only — which provider minted it, when known. */
    provider?: "naap" | "pymthouse" | "daydream";
    /** keyScheme() output: naap | pmth | pmth-composite | sk | opaque */
    scheme?: KeyScheme;
    /** Present only for demo callers, preserving today's AuthContext. */
    isDemo?: boolean;
    demoIpHash?: string;
  };
}

/** Bearer in, ResolvedCredential out. The single mode-selection site. */
export function resolveAuth(
  headers: Headers,
  demoIpHash?: string,
): ResolvedCredential;

Adapter, not rewrite. buildStoryboardMcpServer takes an AuthContext today (mcp-http.ts:99). PR-02 keeps that signature and derives it from the ResolvedCredential: { apiKey: rc.forwardBearer, isDemo: rc.metadata?.isDemo, demoIpHash: rc.metadata?.demoIpHash }. Zero tool files change in the entire plan — that is the ISP guarantee and it is checked by a diff-scope assertion in every PR's self-review.

6. The PR-cycle LOOP

Every PR in §5 runs the same eight-step loop. The loop exists to make one thing structurally impossible: merging a change whose flag-OFF behavior has not been measured against a baseline captured from the same session.

#StepExit condition (all must hold to proceed)
1Baseline — capture current behavior for the rows this PR could touchBaseline artifacts saved before any code is written. A baseline captured after the change is not a baseline.
2Branch from latest main, one PR = one concernPR maps to exactly one §5 card. If it needs two cards, it is two PRs.
3Invariant gate — run INV-1…INV-6 unmodifiedGreen before implementing. If a PR requires editing an invariant test, stop and escalate — that is the plan's tripwire, not a chore.
4Implement to the card's file listDiff-scope assertion holds: no tools/, no sdk-call.ts, no key_routing.py.
5Self-review — author completes the card's checklist in the PR bodyEvery box ticked with evidence, not assertion. Secret scan clean is non-negotiable.
6E2E on preview, flag OFF and ONFlag OFF result is byte-identical to the step-1 baseline. Flag ON matches the card's acceptance.
7Merge with the flag OFF, then verify in prodProd verification from the card passes. No PR is merged with a flag ON. Flag flips are a separate, gated act (§9).
8Record the rollback + revert-safety note on the merge commitThe next engineer can revert without re-deriving the dependency order.
Anti-pattern review is part of every approval. A reviewer must explicitly confirm the diff contains none of AP-1…AP-11 (§3.5). The three that have historically slipped through are AP-1 (a provider if leaking outside resolve.ts), AP-6 (a "small" extra flag), and AP-9/AP-11 (a convenient but non-durable token store).
