Quick read — one-page overview

Problem: Storyboard MCP is bearer-only today. Users paste a long-lived pymthouse composite key into Claude. OAuth metadata returns 404 (storyboard/app/.well-known/oauth-protected-resource/route.ts).

Solution shape: Storyboard becomes an MCP OAuth broker (RFC 9728 PRM + PKCE) with a thin Auth Resolution Layer (§2): Bearer in → forwardBearer out. OAuth mint providers (A/B) run at connect time only; inference/SDK/signing never branch on auth mode.

1. Executive summary

Recommendation: Ship Scenario A first (NaaP sign-in → composite mint). Design Scenario B in parallel for teams that want pymthouse-only billing with no NaaP account. Both plug into the same thin Auth Resolution Layer (§2); only the OAuth mint provider differs. The signer / gateway / orchestrator tail is identical and auth-agnostic.

2. Architecture principles & Auth Resolution Layer

2.1 Core principles

  • Single responsibility: Authentication UX (OAuth connect, key paste) is separate from billing execution (signer routing, payment, orchestration).
  • Reuse existing tail: OAuth paths mint the same composite shape the paste-key path already uses — no new signer protocol, no JWT-only shortcut in MVP.
  • Additive OAuth: One flag (MCP_OAUTH_ENABLED, default OFF). Bearer path byte-identical when OFF (INV-1, storyboard/docs/superpowers/plans/2026-07-10-mcp-gap-closure.md).
  • Credential-shape routing downstream: SDK classify_key() decides signer URL from bearer prefix/segment — never from OAuth provider name.
  • No runtime mode picker in inference: Tri-mode selection happens at connector setup + Auth Resolution only.

2.3 Interface contract — ResolvedCredential

/** Storyboard Auth Resolution output — consumed by sdkCall only. */
interface ResolvedCredential {
  /** Billing plane hint for logging/metrics — NOT used by SDK (SDK re-classifies). */
  plane: "daydream" | "pymthouse";
  /** Verbatim bearer forwarded to SDK POST /inference — always sk_* or app_*_pmth_*. */
  forwardBearer: string;
  metadata?: {
    source: "api_key" | "oauth_session" | "demo";
    provider?: "naap" | "pymthouse" | "daydream";  // audit only
    scheme?: string;  // keyScheme() — naap | pmth | sk | opaque
  };
}

2.7 Scope trim — defer to reduce over-engineering

  • Defer PR-F provider registry to Phase +3 — MVP uses one env-selected mint provider (MCP_OAUTH_PROVIDER), not hot-swappable registry.
  • Defer device-flow provider (B5) unless web_ registration blocked — auth-code path is sufficient for Claude.
  • Defer authorize-time A/B picker — separate deployments or connector templates instead.
  • Do not add a third OAuth flag beyond MCP_OAUTH_ENABLED + provider env; avoid MCP_OAUTH_MODE, TRI_MODE_ENABLED, etc.
  • Single mint output shape for billed pymthouse MCP: composite only — reuses existing DMZ webhook + SDK DIRECT path.

4. Current state (as-is)

  • Storyboard MCP — bearer-only; extractAuth forwards opaque Bearer to SDK (lib/mcp-server/auth.ts, sdk-call.ts). OAuth stubs return 404 JSON. Provider-neutral: accepts sk_, app_*_pmth_*, naap_, pmth_, opaque ≥16 chars.
  • NaaP validate (legacy canary) — POST /api/v1/keys/validate accepts naap_; resolveSignerEndpoint emits composite in endpoint form (pymthouse-adapter.ts). Used when SDK SIGNER_FROM_VALIDATE=1 — not prod default (STORYBOARD-SIGNER-ROUTING.md).
  • pymthouse OIDC — full AS at {origin}/api/v1/oidc; RFC 8693 exchange; composite app_<24hex>_pmth_<secret> (docs/builder-api.md).
  • SDK routing (target prod path) — KEY_ROUTING_FROM_ENV=1: sk_* → Daydream STATIC; app_*_pmth_* → pymthouse DIRECT (key_routing.py). Legacy naap_* validate RESOLVE path retired in key_routing. Prod today: flags often unset → static Daydream signer for all keys.

5. Problem / gap

Claude MCP OAuth requires RFC 9728 Protected Resource Metadata + authorization server + token the MCP server verifies. Storyboard advertises bearer-only, no OAuth. There is no bridge from browser sign-in to a signer-accepted credential on MCP tool calls.

7.2 As-is gap for pymthouse-direct MCP OAuth

  • MCP endpoint is Storyboard, not pymthouse. RFC 9728 PRM must be served at the Storyboard MCP URL; pymthouse cannot be the protected resource.
  • Public app_ client cannot do auth-code. Claude MCP OAuth expects authorization-code + PKCE. pymthouse registers auth-code only on confidential web_ sibling (confidential-web.ts, builder-api.md §Client shapes).
  • Post-login composite mint needs M2M. Builder POST …/keys requires M2M Basic — Storyboard must hold m2m_* + secret env vars (today NaaP holds these).
  • Device-flow-only path exists but UX-poor for Claude. pymthouse native device UI at {origin}/oidc/device works without NaaP, but is not standard MCP OAuth UX.
  • No Storyboard OAuth broker yet. Same gap as Scenario A — new code in both scenarios.

7.4 Alternative sub-path — device flow (deferred)

Deferred per §2.7 — only if web_ registration blocked. Storyboard broker could initiate RFC 8628 device authorization against public app_ client. pymthouse documents this (builder-api.md §Device) but UX is poor for Claude; not MVP.

7.5 Feasibility verdict — Scenario B

Conditionally feasible — not turnkey today.
  • Ready: pymthouse OIDC AS, Builder composite mint, DMZ composite/JWT auth, RFC 8693 exchange.
  • Build required: Storyboard MCP OAuth broker (same as A) + pymthouse web_ client registration with Storyboard redirect URIs + Storyboard env for M2M mint + SDK composite-direct routing.
  • Not feasible as-is: Point Claude directly at pymthouse with zero Storyboard broker; or use public app_ for auth-code PKCE (explicitly forbidden in syncPublicClientGrantTypes).

  • PRM authorization_servers: ["https://pymthouse.com/api/v1/oidc"] (issuer origin — avoid path-only discovery bugs per Claude.ai #82).

  • Upsert app user first: POST …/apps/{appId}/users (same as NaaP ensureAppUserProvisioned).

  • SDK KEY_ROUTING_FROM_ENV=1 on inference nodes (shared with A — no OAuth coupling).
  • Claude connector → sign in at pymthouse → create_media flux-schnell → OpenMeter delta on user's pymthouse app wallet.

Only if B0 blocked — see §2.7

13. Security considerations

  • Never return composite to Claude — bind server-side; MCP tokens revocable.
  • PKCE S256 mandatory on MCP OAuth broker (Claude requirement).
  • PRM resource must exactly match MCP URL users enter.
  • Scenario B: Storyboard M2M secret in server env only — same sensitivity as NaaP PYMTHOUSE_M2M_CLIENT_SECRET today.
  • Issuer discovery: use full issuer URL https://pymthouse.com/api/v1/oidc in PRM; test Claude.ai path-aware discovery (#82).
  • Per-user isolation: composite mint bound to authenticated sub; no cross-user credential reuse in oauth-store.

15. Tri-mode coexistence — API key + OAuth A + OAuth B

Feasibility: YES — all three modes are providers into the Auth Resolution Layer (§2), not branches in inference code. Mode 3 (API key paste) uses PassthroughKeyProvider; Modes 1–2 use OAuthSessionStore populated at connect time by Scenario A or B mint providers. Downstream always receives forwardBearer only.

15.1 Three credential providers (not three inference paths)

Provider P0 — API key

Passthrough at resolve time
  • Input: sk_* or app_*_pmth_* in Bearer header
  • Output: same token as forwardBearer
  • Shipped today

Provider P1 — OAuth A mint

Connect: NaaP → composite
  • Runs once at OAuth token issuance
  • Stores composite in oauth-store keyed by mcp_at_*
  • Resolve: session → composite forwardBearer

Provider P2 — OAuth B mint

Connect: pymthouse → composite
  • Same oauth-store contract as P1
  • Different upstream IdP + mint caller (Storyboard M2M)
  • Same forwardBearer shape out

User choice: Connector configuration level — bearer template vs OAuth template; OAuth A vs B via deployment env (MCP_OAUTH_PROVIDER) or separate MCP URLs. See §2.5 anti-patterns — no runtime picker in one connector.
