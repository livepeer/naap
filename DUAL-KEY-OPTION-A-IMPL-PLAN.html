1 · What changed vs the original Option A

Original Option A (DUAL-KEY-SIDE-BY-SIDE-DESIGN.html:202-297) said: the SDK service already routes by key format (token.startswith("naap_") in _resolve_validate_session — sdk-service-build/app.py:854, called by _effective_signer  :904-923); the only work is to turn the process-wide gates ON and add a fail-closed guard for a naap_ key with no session. This plan keeps that spirit but adds three operator-controlled, default-off improvements:

ImprovementOriginal Option AThis plan
1. Path→orch pinning (pymthouse) Silent: pymthouse path may land on the live-runner orch or fall open to byoc-staging-1 (LR failure fails-open to BYOC — LR-3ORCH-INFRA-ASSESSMENT.md:101). Optional flag pins the pymthouse path to the live-runner orch ONLY (no BYOC fall-open). Default OFF = today's fail-open preserved.
2. Path→orch pinning (Daydream), same flag Not addressed. The same single flag symmetrically pins the Daydream path to byoc/daydream ONLY (never the LR orch). Default OFF = unchanged.
3. Configurable key→path patterns Hardcoded startswith("naap_") discriminator. Env-driven glob patterns (KEY_PATTERN_PYMTHOUSE / KEY_PATTERN_DAYDREAM) with first-match precedence and a fail-closed policy for unmatched keys. Default reproduces the hardcoded behavior exactly.

Design choices, justified

  • Glob, not regex. Key discriminators are literal-prefix tokens (naap_, sk_live_, app_…_pmth_). Glob (fnmatch: *, ?) is operator-legible, matches the existing sk_live_* mental model, and eliminates ReDoS / catastrophic backtracking and accidental over-broad patterns. If true regex power is ever needed, add KEY_PATTERN_SYNTAX=glob|regex later — not now.
  • First-match precedence. Pymthouse patterns are checked before Daydream patterns; the first list that matches wins. Rationale: native naap_/composite forms are the more specific, higher-risk routing (they must never leak to the shared wallet), so they take priority. Patterns SHOULD be disjoint; validate-envs.sh warns if a sample key matches both lists.
  • Fail-closed for unmatched (FINAL default when the engine is enabled — OQ-3 resolved). An unmatched key today falls through to the Daydream signer and silently bills the shared Daydream wallet — the HIGH risk R1 in the original design (DUAL-KEY-SIDE-BY-SIDE-DESIGN.html:317-321). Rejecting is safer. Because the whole engine is gated OFF by default (KEY_ROUTING_FROM_ENV=0), defaulting the inner policy to fail_closed introduces zero regression at merge; operators who want the legacy fall-through can set KEY_ROUTING_UNMATCHED=daydream.
  • One flag for both pins (as explicitly requested). Trade-off: a single ORCH_PIN_BY_PATH is atomic, symmetrical, and one-switch to roll back — but you cannot pin one side while leaving the other free. If independent control is later needed, split into ORCH_PIN_PYMTHOUSE / ORCH_PIN_DAYDREAM; ship one flag now.

7 · Rollout / enablement & rollback

Enablement (per-instance, additive)

  1. Phase 0 — merge all PRs, all flags OFF. Production is byte-identical; nothing routes differently.
  2. Phase 1 — one canary instance: KEY_ROUTING_FROM_ENV=1 with default patterns (naap_*, sk_*) and KEY_ROUTING_UNMATCHED=daydream first → verify routing is identical to legacy (rows 6/7).
  3. Phase 2: flip KEY_ROUTING_UNMATCHED=fail_closed on canary → verify unmatched keys reject (row 8) and known keys still pass.
  4. Phase 3: set ORCH_PIN_BY_PATH=1 on canary after confirming the DMZ signer is fixed-capable (OQ-1) → verify naap→LR-only (row 4/10) and daydream→byoc-only (row 2/11).
  5. Phase 4 (optional): NAAP_FAIL_CLOSED=1.
  6. Promote instance-by-instance once each phase is green.

Rollback

  • Every control is an env var — unset it (or set 0) + restart → byte-identical to the prior state. No image rebuild required (all env-gated).
  • Honor the guard rail: keep SIGNER_FROM_VALIDATE/AUTH_VALIDATE_URL paired (validate-envs.sh:141-155).
  • Instant partial rollback: ORCH_PIN_BY_PATH=0 restores LR→BYOC fail-open (removes the pin's fail-closed blast radius) without touching key routing.
