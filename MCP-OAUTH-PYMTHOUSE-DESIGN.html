MCP OAuth + PymtHouse Signer — Design Proposal

Let users connect Claude (or similar MCP clients) to the Livepeer Agent / Storyboard MCP endpoint via OAuth sign-in — no pasted composite app_<id>_pmth_<secret> key — while preserving the existing billed path: composite bearer → pymthouse remote signer /generate-live-payment → orchestrator → metering.

1. Executive summary

Recommendation: Add a Storyboard-hosted MCP OAuth broker (extend the existing PR-E plan in storyboard/docs/superpowers/plans/2026-07-14-pr-e-oauth-connect.md) with a pymthouse/NaaP credential provider. After browser sign-in, the broker server-side mints or resolves the same credential the billed path already accepts — preferably a composite app_<24hex>_pmth_<secret> via NaaP's existing createPymthouseApiKey — and binds it to a short-lived MCP session token. Storyboard continues to forward an opaque bearer to the SDK service; Claude never sees the composite secret.

Today, Storyboard MCP is bearer-only: the client must paste a long-lived API key into the connector's Authorization header (livepeer/storyboard/lib/mcp-server/auth.ts). The pymthouse billed path expects either (a) a composite bearer forwarded directly to the remote signer DMZ identity webhook, or (b) a naap_ key resolved through NaaP POST /api/v1/keys/validate into endpoint-form signerSession.{url, headers} with composite inside headers.Authorization (apps/web-next/src/lib/billing/pymthouse-adapter.ts :: resolveSignerEndpoint). OAuth for MCP (RFC 9728 + Claude connector requirements) is not implemented; Storyboard deliberately returns JSON 404 stubs at /.well-known/oauth-* stating bearer-only auth.

2. Current state (as-is)

2.1 Storyboard MCP — bearer passthrough

Verified via livepeer/storyboard on GitHub (main, 2026-08-07):

  • app/api/mcp/route.ts — stateless MCP endpoint; auth = caller Authorization: Bearer ….
  • lib/mcp-server/auth.ts — extracts bearer; no composite parsing, exchange, or OAuth. Accepts opaque tokens (sk_, naap_, app_*_pmth_*, etc.).
  • lib/mcp-server/sdk-call.ts — forwards apiKey unchanged to SDK /inference.
  • lib/sdk/provider-server.ts (SB-4) — when STORYBOARD_PROVIDER_SWITCH=1 + NAAP_PROVIDER=naap, targets NaaP SDK front door (NAAP_BASE_URL); default OFF → sdk.daydream.monster.
  • app/.well-known/oauth-protected-resource/route.ts — returns 404 JSON: "Bearer-only auth; no OAuth."

2.2 NaaP — validate front door & pymthouse adapter

  • POST /api/v1/keys/validate (apps/web-next/src/app/api/v1/keys/validate/route.ts) — accepts native naap_ keys only (provider-token passthrough disabled at line 114–117). Returns signerSession when per_key_remote_signer flag ON.
  • PymthouseAdapter.resolveSignerEndpoint (pymthouse-adapter.ts:300–374) — emits endpoint form with composite Bearer (fast path via PYMTHOUSE_API_KEY env) or mints composite via createPymthouseApiKey.
  • exchangeApiKeyForSignerSession (pymthouse-client.ts:323–404) — RFC 8693 at POST …/apps/{clientId}/oidc/token; composite forwarded verbatim to DMZ without exchange.
  • POST /api/v1/auth/providers/pymthouse/start (auth/providers/…/start/route.ts) — NaaP session + CSRF → server mints long-lived composite via createPymthouseApiKey (Dashboard parity).
  • POST /api/pymthouse/keys/exchange — public composite → signer JWT exchange (@pymthouse/builder-sdk/signer/server).
  • NaaP login OAuth (Google/GitHub) exists for the web dashboard (apps/web-next/src/lib/api/auth.ts) — not wired to MCP.

2.3 pymthouse — OIDC, composite, signer

  • Composite format: app_<24hex>_pmth_<secret> (Builder API 0.6.0; pymthouse/docs/builder-api.md).
  • Public app_ client: device flow + token exchange; no authorization-code redirects on app_ (auth-code lives on confidential web_ sibling).
  • RFC 8693 token exchange: user JWT or API key → signer JWT or opaque session (pymthouse-client.ts, mintOpaqueSignerSessionForExternalUser).
  • Remote signer DMZ identity webhook accepts JWT or composite Bearer; bare opaque pmth_ rejected on /generate-live-payment (pymthouse-adapter.ts:271–277, BILLED-E2E-BLOCKER-AUDIT.md Run 50).
  • Device flow (RFC 8628) + NaaP-side approval already implemented (pymthouse-device-initiate.ts, docs/pymthouse-integration.md §Device login).

2.4 simple-infra SDK service — signer routing

From STORYBOARD-SIGNER-ROUTING.md (code refs to livepeer/simple-infra/sdk-service-build/app.py):

  • Decision node: _effective_signer — pymthouse path only when SIGNER_FROM_VALIDATE=1, AUTH_VALIDATE_URL set, bearer is naap_, and validate returns endpoint-form signerSession.
  • Production default: static SIGNER_URL=https://signer.daydream.live (lv2v / Daydream metering).
  • Gateway _payment_type_for_signer: hostname signer.daydream.live → lv2v; else → byoc.
  • Composite direct to DMZ signer verified in probe scripts (pymthouse-e2e.md, Run 50–57) — bypasses validate; hosted SDK node may still need explicit composite routing (gap — see §11).

3. Problem / gap

Why composite key paste is required today: MCP clients authenticate to Storyboard with a static bearer. Claude's OAuth connector expects RFC 9728 Protected Resource Metadata, an authorization server, and a token the MCP server verifies — Storyboard explicitly advertises no OAuth. There is no bridge from "user signed into NaaP/pymthouse in a browser" to "MCP request carries a signer-accepted credential."

4. Proposed OAuth architecture (to-be)

4.1 Design principles

  • Reuse, don't reinvent: composite mint (createPymthouseApiKey), RFC 8693 exchange, DMZ webhook auth, and SDK gateway payment types stay unchanged.
  • Secrets server-side: Claude receives an MCP session token (opaque, short TTL); composite never returned to the client.
  • Flag-gated zero regression: MCP_OAUTH_ENABLED default OFF — bearer path byte-identical (PR-E INV-1 pattern).
  • Provider plug-in: extend PR-F provider registry with pymthouse / naap credential issuers.

5. Step-by-step user journey

  1. Add connector in Claude — URL: https://storyboard.daydream.monster/api/mcp (or role-scoped variant). No Authorization header field (OAuth mode).
  2. Claude probes PRM — GET /.well-known/oauth-protected-resource → JSON listing Storyboard AS + scopes (e.g. sign:job mcp:tools).
  3. Lazy auth on first tool call — unauthenticated request → 401 + WWW-Authenticate: Bearer resource_metadata="…" (Claude lazy-auth spec).
  4. Browser OAuth — Claude opens /api/mcp/oauth/authorize (PKCE S256) → redirect to NaaP login (or pymthouse device approval in phase 2).
  5. Credential bind (server) — on success, broker calls NaaP internal mint: 
    POST (internal) createPymthouseApiKey
  externalUserId = naapUser.sub
→ composite app_<24hex>_pmth_<secret>  // never sent to Claude
  6. Token issue — Claude receives MCP access token (opaque, ~1h TTL, refresh optional).
  7. MCP inference — tools/call create_media with Authorization: Bearer <mcp-token> → extractAuth resolves composite → sdkCall → SDK /inference.
  8. Payment — SDK forwards composite Bearer to pymthouse DMZ /generate-live-payment → identity webhook validates composite → ticket signed → orchestrator → asset URL → OpenMeter ingest.

8. Security considerations

  • Never expose composite to MCP clients. Bind server-side; MCP tokens are revocable, short-lived, and useless without Storyboard verification.
  • PKCE S256 mandatory on MCP OAuth (Claude requirement; PR-E already specifies).
  • PRM resource must match the exact MCP URL users enter (including path) — Claude validates strictly.
  • Authorization server discovery: list pymthouse/NaaP issuer first in authorization_servers; avoid path-only issuers that break Claude.ai fallback (see anthropics/claude-ai-mcp#82).
  • Rate limits on OAuth token endpoint and mint calls (mirror auth/providers/pymthouse/start rate limit).
  • Team / billing isolation: composite mint must bind to the signed-in NaaP user's billing account; no cross-user credential reuse in oauth-store.
  • Audit: log mint events without secrets ([billing-auth:pymthouse] pattern).
  • CSRF: NaaP mint endpoints stay session+CSRF protected; Storyboard broker uses separate OAuth state/nonce store.

9. Phased implementation plan

Phase 0 — Preconditions (ops, no OAuth code)

Gate: billed composite path green on staging

  • Enable SB-4 canary + SIGNER_FROM_VALIDATE=1 on staging SDK node.
  • Confirm validate emits endpoint form with composite (pymthouse-e2e.md Stage 0).
  • Confirm DMZ /generate-live-payment accepts composite (Run 50 baseline).

Phase 1 — MVP OAuth (NaaP sign-in → composite bind)

Gate: Claude URL-only connector → one billed flux-schnell image

  1. Storyboard: real PRM + AS metadata when MCP_OAUTH_ENABLED=1 (Task 1, PR-E).
  2. Storyboard: OAuth broker routes + encrypted/KV session store (Task 2).
  3. NaaP: thin POST /api/v1/internal/mcp/mint-credential — session auth + mint composite (wraps existing createPymthouseApiKey).
  4. Storyboard: naap provider issueCredential calls internal mint.
  5. Storyboard: extractAuth resolves MCP token → composite (Task 4).
  6. simple-infra: _effective_signer branch for composite bearer OR use naap_ mint + validate path.
  7. E2E: Claude connector → sign in → create_media → OpenMeter delta.

Phase 2 — pymthouse-native device login option

  • Broker provider uses existing RFC 8628 + NaaP pymthouse-device-approve flow.
  • Map device user JWT → composite via same Builder mint APIs.
  • Emit URL-only connector docs on get-started page.

Phase 3 — Production hardening

  • Prod SB-4 + SDK env rollout (STORYBOARD-SIGNER-ROUTING.md checklist).
  • Claude connector review (mcp-review@anthropic.com if custom auth mode).
  • Refresh token rotation, credential rotation policy, per-user spend caps.
