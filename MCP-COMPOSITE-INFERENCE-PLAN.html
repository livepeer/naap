MCP → Composite-Key Inference — End-to-End Plan

How to make the Storyboard MCP perform inference with a pymthouse composite bearer (app_<clientId>_pmth_<secret>) so the SDK forwards it DIRECT to the pymthouse signer — no re-validation. Planning & investigation only; no code, deploy, or flag changes were made.

TL;DR — The composite key is the pymthouse signer credential. It travels as the MCP caller's Authorization: Bearer and is forwarded verbatim to sdk.daydream.monster/inference, where the pattern engine classifies app_*_pmth_* as pymthouse and — with PYMTHOUSE_COMPOSITE_DIRECT=1 — skips /keys/validate and posts the composite straight to PYMTHOUSE_SIGNER_URL. On the MCP side there is nothing to change but the bearer value: the MCP server forwards whatever bearer the caller presents (per-call passthrough, provider-neutral).

1. Goal & token recap

TokenWhat it isWho accepts itSigner behavior
naap_xxx NaaP front-door key Only NaaP /keys/validate RESOLVE validate → mint session
app_<clientId>_pmth_<secret> Composite bearer — the session output the pymthouse signer accepts directly The pymthouse signer directly DIRECT forward as-is, no validate

The composite cannot be re-validated: Run 68 showed composite → /keys/validate → 404 → BYOC fallback → 502. So the goal is to get the composite to the SDK and have the SDK take the DIRECT path (skip validate) to the signer.

3. Config surface — the actionable steps

3a. MCP side only the bearer changes

The Storyboard MCP is a stateless HTTP MCP server at https://storyboard.daydream.monster/api/mcp. It is provider-neutral: it accepts any opaque bearer ≥ 16 chars and forwards it downstream — it does not require an sk_/naap_ prefix. So the only MCP-side action is to set the client's outbound bearer to the composite.

The bearer is set in the MCP client config header. In this repo's checkout the header is templated from the env var LIVEPEER_AGENT_API_KEY:

// .mcp.json  (Cursor / Claude Code / Codex)
{
  "mcpServers": {
    "storyboard": {
      "type": "http",
      "url": "https://storyboard.daydream.monster/api/mcp",
      "headers": {
        "Authorization": "Bearer ${LIVEPEER_AGENT_API_KEY}"
      }
    }
  }
}
# Set the env the header expands to == the composite:
export LIVEPEER_AGENT_API_KEY='app_<clientId>_pmth_<secret>'

# Or add it inline (Claude Code CLI):
claude mcp add storyboard \
  https://storyboard.daydream.monster/api/mcp \
  --header "Authorization: Bearer app_<clientId>_pmth_<secret>"
Header footgun (from the MCP README): Claude Desktop's mcp-remote needs Authorization:Bearer … with no space after the colon; Claude Code / Cursor / Codex need a space: Authorization: Bearer …. Getting this wrong is the #1 cause of a silent 401.

Per-call vs. static bearer: The MCP server supports per-call passthrough — every request's bearer is forwarded independently (no server-pinned key on the hot path). The MCP client config, however, pins one bearer per configured server entry (the LIVEPEER_AGENT_API_KEY header). To use the composite, set that one header to the composite. There is no per-tool-call key override in the tool arguments — the key is always the connection's Authorization header.

Base URL: the MCP resolves its outbound base via the server provider adapter; the default is https://sdk.daydream.monster. With STORYBOARD_PROVIDER_SWITCH OFF (default) it returns the Daydream/SDK base byte-for-byte, so the composite lands on sdk.daydream.monster/inference where classification + DIRECT-forward run. (Overridable via STORYBOARD_SDK_URL/SDK_URL if ever pointed elsewhere.)

3b. SDK side already being shipped (worker 4288c982)

These are set on sdk-staging-1; nothing here is an action for the MCP owner — listed so the reader knows the DIRECT path is live end-to-end:

  • PYMTHOUSE_COMPOSITE_DIRECT=1 — enables the DIRECT branch (skip validate for composites).
  • PYMTHOUSE_SIGNER_URL=https://pymthouse-production.up.railway.app — where the composite is forwarded.
  • Pattern engine (already ON): KEY_PATTERN_PYMTHOUSE=naap_*,app_*_pmth_* — must include app_*_pmth_*; KEY_PATTERN_DAYDREAM=sk_*; unmatched=daydream; pins OFF.

4. Why validate is skipped for composites (Run 68 root cause)

A composite is the output of a signer session, not an input credential the front door can look up. Sending it to /keys/validate yields 404 (no such key), which then falls back to the BYOC path and dies with 502. Hence two distinct behaviors:

PathInputStepsResult
RESOLVEnaap_…validate → mint signer session → sign → payworks
DIRECTapp_*_pmth_*skip validate → forward composite to signer → sign → payRun 68 Test 1: mint 200 + real asset

Direct-to-signer with the composite is PROVEN GREEN (Run 68 Test 1). The DIRECT flag simply teaches the SDK to reproduce that proven curl---token behavior instead of re-validating.

5. Contrast path — if you instead hold a naap_ key

Then you don't need a composite at all: present the naap_ key as the MCP bearer and let the SDK take the RESOLVE path — it calls NaaP /keys/validate, mints a signer session, and signs. The MCP-side steps are identical (set the bearer to the naap_ key); only the SDK's internal branch differs (validate instead of skip). Use the composite only when you already have a live session-output credential and want to bypass validation.

6. Verification checklist

  • Run one inference via the MCP with the composite bearer (e.g. a small create_media image call).
  • Expect HTTP 200 + a real asset URL in the tool result.
  • SDK logs show validate SKIPPED for the composite (DIRECT branch taken).
  • SDK logs show the forward target host = pymthouse-production.up.railway.app.
  • A signed payment ticket is generated (RemoteType_Fixed).
  • Metering debits <clientId>. Note: the usage-read endpoint was transiently 404 during redeploy — if so, rely on signed-ticket generation as the proof of billing rather than the usage read.

7. Prerequisites & risks

  • Session-scoped The composite is short-lived — NaaP's webhook refreshes/rotates it. The MCP must be able to refresh the bearer; a static header (like LIVEPEER_AGENT_API_KEY) will go stale when the session rotates. See open question below.
  • Flag dependency PYMTHOUSE_COMPOSITE_DIRECT=1 and PYMTHOUSE_SIGNER_URL must be set on the SDK; pattern engine must include app_*_pmth_*.
  • Met A RemoteType_Fixed-capable signer + LR orch serving the fixed caps.
  • Open dependency Landing + deploy of worker 4288c982's SDK DIRECT change (on livepeer/simple-infra). Until deployed to the SDK the MCP path will still hit RESOLVE and 404/502 on a composite.
  • Routing Keep STORYBOARD_PROVIDER_SWITCH in a state where the MCP's outbound base is sdk.daydream.monster (the SDK that runs classify + DIRECT). If ever routed to a NaaP front door that re-validates, the composite would 404.

8. Open questions for owners

  1. MCP bearer refresh: Does the Storyboard MCP client support a rotating/refreshable composite bearer, or only a static header value? The .mcp.json header is a single static ${LIVEPEER_AGENT_API_KEY}; if the composite is session-scoped, who/what re-writes that header (or the env) when NaaP rotates it? (If only static, a short-lived composite will expire mid-session — need a refresh mechanism or a longer-lived credential.)
  2. Deploy gate: Confirm worker 4288c982's DIRECT change is deployed to the SDK the MCP actually targets (sdk.daydream.monster), not only to sdk-staging-1, before end users are told to use composites.
  3. Metering read: Is the usage-read 404 fully resolved post-redeploy, so the checklist can verify <clientId> debits directly rather than inferring from ticket generation?
